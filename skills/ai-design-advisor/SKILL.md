# AI Design Advisor

生成AIの設計を、用語の説明ではなく **選ぶ判断** として返す。
根拠は `knowledge/canonical/` のみ。未精査の項目は推奨を確定しない。

想定読者は、ベンダーに依頼する業務側と、構成を素早く切りたいエンジニア。

## いつ使うか

- ユースケースから推奨構成を出したいとき
- ベンダー提案（LoRA する、エージェントにする、最大モデルにする等）を点検するとき
- SLM/LLM、RAG、エージェント化、権限の渡し方など、単一次元の判断が欲しいとき
- チェックリスト型で要件を洗い出したいとき（同じ出力型を項目ごとに埋める）

## 進め方

### Step 1: 要件を抽出する

入力から次を取る。無いものは「未確認」とし、推測で埋めない。

- 何をするシステムか（コンシューマ向けチャット、社内検索、分類、エージェント作業 等）
- 誰が使うか、データは外に出せるか
- 知識は最新・社内固有・出典が要るか
- レイテンシ・コストの厳しさ
- ツールや書き込みが要るか
- 合格の線（あるなら）

足りない軸は Step 4 の「追加で確認」に回す。要件定義の全文がなくても、分かっている範囲で推奨してよい。

### Step 2: 次元を順に当てる

各次元で、対応する canonical ノートを読む。ノートに無いことは書かない。

| 順 | 次元 | 読む先 |
| --- | --- | --- |
| D1 | モデルクラス | `knowledge/canonical/d1-model-class/selection.md` |
| D2 | Temperature / Effort | `knowledge/canonical/d2-parameters/temperature-and-effort.md` |
| D3 | コンテキスト・知識 | `knowledge/canonical/d3-context-knowledge/` |
| D4 | プロンプトの住所 | `knowledge/canonical/d4-prompt-dialogue/` |
| D5 | RAG | `knowledge/canonical/d5-rag/when-and-how.md` |
| D6 | エージェント化 | `knowledge/canonical/d6-agent/` |
| D7 | Fine-tune の要否 | `knowledge/canonical/d7-finetune/when-to-finetune.md` |
| D8 | セキュリティ | `knowledge/canonical/d8-security/` |
| D9 | 運用・評価 | `knowledge/canonical/d9-ops-eval/` |
| X | キャッシュ・レイテンシ切り分け等 | `knowledge/canonical/x-cross-constraints/` |

D7 の手法名・再学習手順は `methods-unreviewed.md` / `ops-unreviewed.md` がある。**推奨に使わない。**

### Step 3: 衝突を解消する

次元単体の推奨が食い違うときは、横断制約を優先する。

- データを外に出せない → D1 は SLM / オンデバイス寄り。クラウド LLM 前提を捨てる
- 出典・更新が要る → D7 はしない。D5
- 書き込み・課金・個人情報更新がある → D6/D8 は permission + HITL。authority を広げない
- 体感が厳しい → D2 の Effort を上げない。D5 の Agentic RAG に進まない。X の prefill/decode を見る

### Step 4: 出力する

下のフォーマットを守る。各次元は「推奨 / 根拠 / 代替 / リスク」。
根拠は canonical のファイル名でよい。未精査は「情報不足」と書く。

## 出力フォーマット

```markdown
## 設計判断レポート

**対象**: [ユースケースを1–3文]
**前提（入力から取れたもの）**: [制約。未確認は未確認と書く]
**日付**: YYYY-MM-DD

### 推奨構成（要約）

- モデル: …
- パラメータ: Temperature … / Effort …
- 知識: RAG する・しない / Memory …
- 実行系: Plain / Skill / Tool / Agent（段）
- Fine-tune: しない / 要否のみ検討
- 権限と止め方: …
- 測り方: …

### 次元別

| 次元 | 推奨 | 根拠 | 確度 |
| --- | --- | --- | --- |
| D1 モデル | | canonical ファイル名 | 確定 / 条件付き / 情報不足 |
| D2 パラメータ | | | |
| D3 コンテキスト | | | |
| D4 プロンプト | | | |
| D5 RAG | | | |
| D6 エージェント | | | |
| D7 Fine-tune | | when-to-finetune / 手法は情報不足 | |
| D8 セキュリティ | | | |
| D9 運用 | | | |
| X 横断 | | | |

### 詳細

次元ごとに短く:
- 推奨
- なぜ（制約との対応）
- 代替（いつこちらへ倒すか）
- やってはいけないこと

### ベンダーに渡すとき

依頼側がそのまま使える文言:
- やること / やらないこと
- 合格の線（書ける範囲）
- 提案を受けたら疑うフレーズ（例: 「まず LoRA」「全部エージェント」）

### 追加で確認すべきこと

入力に無く、推奨が分岐する問いだけ列挙する。
```

確度:

- **確定** — canonical があり、入力の制約と衝突しない
- **条件付き** — ある前提が満たされたときだけ
- **情報不足** — 未精査、または入力が足りない

## やってはいけないこと

- canonical に無い数値・製品デフォルトを「公式」として書く
- D7 で LoRA / フル FT / 学習率を推奨する
- 要件が曖昧なまま構成を一意に決めたように見せる
- ホスト製品のファイル名（CLAUDE.md 等）を、他環境の必須手順として書く。原則は常駐 / 条件付き / オンデマンド

## チェックリスト型で使うとき

Web / 対話で項目を埋める場合も、同じ表と要約を最終出力にする。
項目が空の次元は ➖ 相当として「情報不足」にする。無理に埋めない。
深掘り問の種は `knowledge/canonical/_field-questions.md`。
