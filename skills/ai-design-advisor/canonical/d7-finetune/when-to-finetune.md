## 判断の問い

- プロンプトと RAG で、品質・形式・コストのどれがまだ足りないか
- 足したいのは **変わらない型**（口調・書式・狭い分類）か、**変わる知識**か
- 出典・権限・最新性が要るか（要るなら FT より RAG）
- 大きいモデルの呼び出し回数が、コストの本体になっているか

## 推奨パターン

**デフォルトは Fine-tune しない。** 先に D4（指定と例）→ D5（根拠と更新）→ D1（小さいモデルへ上げ下げ）を試す。Fowler / AWS Lens も同方向。

| やりたいこと | 先に見る場所 | FT か |
| --- | --- | --- |
| 最新・社内文書・出典 | D5 RAG | しない。更新が追いつかない |
| 権限の違う文書 | D5 + D8 | しない。重みに混ぜると切れない |
| 「答えられない」経路 | D3 / D5 | しない |
| 今回限りの依頼・役割 | D4 プロンプト | しない |
| 口調・書式・社内テンプレを安定させたい | D4 の例示と構造化出力 | 例で足りなければ **疑う** |
| 狭い分類・抽出を大量に安く回したい | D1 の SLM / ルーティング | 汎用モデルが高すぎるなら **疑う** |
| 大きいモデルの答えを小さいモデルに移したい | D1 + 本次元の蒸留 | 型が固まったあと **疑う** |

FT を開いてよい合図（すべて揃う必要はないが、どれか一つでは弱い）:

1. 出したい **形式・口調・ラベル集合が安定**している（週次で定義が変わらない）
2. 同じ仕事を **十分な正解例**で示せる（評価セットも作れる）
3. プロンプトと RAG を直しても、ずれが **系統的に残る**（ランダムな幻覚ではない）
4. 推論コストまたはレイテンシが支配的で、小さい特化モデルに落とす価値がある

やってはいけない合図:

- 知識が頻繁に変わる（商品、規程、FAQ の中身）
- 根拠を出せることが要件
- データが少ない、またはラベルが汚い
- 「賢くするため」だけ（一般能力の底上げは FT の仕事ではない）
- ベンダー提案が手法名（LoRA 等）から入っている（要否が先）

コンシューマ向けチャットボットの既定: **FT しない。** ナレッジは RAG、口調は短い常駐方針 + 例、難しい問い合わせだけ大きいモデルへ。口調がどうしても安定せず、かつ例が大量にあるときだけ D7 を再開する。

## よくある失敗

- RAG の代わりに FAQ を重みへ焼く
- 例が数十件しかないのに LoRA する
- 評価セットを作らず「っぽくなった」で本番へ
- ベースモデルを上げたあと、古い FT を載せ続ける

## 代替・例外

- 手法の選択（フル / LoRA / QLoRA / 蒸留）と再学習の回し方は [methods-unreviewed.md](./methods-unreviewed.md) / [ops-unreviewed.md](./ops-unreviewed.md)。ここでは決めない。
- 選好学習（RLHF 等）は「要否」の外側。人間の好みを報酬にする話であり、知識注入ではない。未精査。
