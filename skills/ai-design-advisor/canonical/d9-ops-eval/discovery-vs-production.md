## 判断の問い

- この仕事は、まだ形が分かっていないか（発見）、形が分かっているか（生産）
- **指示書を事前に書けるか**（圧縮レディネス）
- それは「誰にとって」圧縮済みか（先輩の手順は後輩には未圧縮）

## 推奨パターン

万能なやり方はない。局面でモードを分ける。

| | 発見（discovery） | 生産（production） |
| --- | --- | --- |
| いつ | 何を作るか分かっていない | 作るものの形が分かっている |
| やり方 | 壁打ち・探索 | 指示書・フェーズ分割・合格基準の先出し |
| 成果 | 自分の理解の変化 | 再現可能な出力 |
| 制約との関係 | 汚れたコンテキストは捨ててよい | Context Rot / Decay / Sycophancy に正面から当たる |

生産モードの「面倒な型」は儀式ではない。

- フェーズ分割 → Context Rot
- 指示をファイルに外在化 → Instruction Decay
- 合格基準を先に書く → Sycophancy

切り替えの第一鍵はプロジェクト期ではなく **圧縮レディネス**（指示書を書けるか）。第二鍵は **立場**（圧縮は人ごとにやり直す）。

本番サービス（コンシューマ向けボット等）は原則 **生産モード**。探索中のプロンプト実験を本番コンテキストに残さない。

破綻したら生産 → 発見へ戻す（早すぎる圧縮の保険）。

## よくある失敗

- 分かっていないうちにテンプレを強制する
- 圧縮できるのに探索を終わらない
- 探索の長い履歴を本番のコンテキストに混ぜる
- 他人の指示書を「理解済み」と扱う

## 代替・例外

- 同じ案件の中で、理解済み部分は生産、未理解部分は発見、と混在してよい
- 指示書の「100〜150行」は自リポの目安。公式上限ではない
