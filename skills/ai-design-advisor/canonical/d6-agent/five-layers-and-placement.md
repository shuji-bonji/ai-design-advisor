## 判断の問い

新しい決まり・手順・接続・記憶を、どこに置くか。

1. 実行が要るか。値はその都度変わるか。
2. 公式の原文へたどれるか。
3. 会話が終わったあとも残す関係か。
4. 目的と優先順位か。手順と例か。
5. 役割として分けた方がよいか。

## 推奨パターン

五層はサーバ構成ではなく、**担当の分け方**である。

| 層 | 担当 | 置かないこと |
| --- | --- | --- |
| Doctrine | 目的・禁止・優先順位 | 手順の列挙、ツールの呼び方 |
| Agent | 作業の理解と組み合わせ | 知識の本体、外部システムの中身 |
| Skills | 変わらない知識と手順 | 実行、いまこの瞬間の値 |
| Memory | 会話をまたぐ関係 | その場限りのプロンプト、原文そのもの |
| MCP | 外のシステムへの接続・事実取得 | 判断の物差し、静的な手順書 |

配置の判定:

- 実行が要る / 値が都度変わる → **MCP**
- 会話のあとも残す関係 → **Memory**
- 目的・禁止・優先順位 → **Doctrine**
- 役割として分ける → **Agent（サブエージェント含む）**
- それ以外の変わらない知識・手順 → **Skills**

法令・RFC 等の原文は推測で埋めない。原文へつなぐなら MCP。組織の決まりと手順は Skills。何を優先するかは Doctrine。

判断が要らない処理は普通のプログラムでよい。人間が自分で判断する操作は公式 CLI のままでよい。**何でも MCP にしてはならない。**

## よくある失敗

- 五層をサーバ台数や製品画面の図だと思う
- サブエージェントを MCP の代わりだと思う（仕事の分け方であり接続ではない）
- Skills に原文をコピーして終わりにする
- 目的・禁止を毎回のプロンプトにだけ書く
- Memory をただのキャッシュだと思う

## 代替・例外

- ホスト製品（Claude Code 等）は層の名前ではない。製品はホスト、層は担当。
- 一つのファイルに複数層の話が混ざることはある。置く場所はファイル名ではなく中身の担当で決める。
