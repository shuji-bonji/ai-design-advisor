## 判断の問い

- この入力は「容量があるから全部載せてよい」と思っていないか
- 重要な指示は先頭・末尾・条件付きのどれに置くか
- 事実と「知らない」をモデルの自己申告に任せていないか

## 推奨パターン

これらはバグではなく、Transformer 系に繰り返し現れる制約である。製品固有の欠陥として扱わない。

| 問題 | 一言 | 設計への含意 |
| --- | --- | --- |
| Context Rot | トークンが増えると品質が落ちる | 窓の上限まで使わない。実効予算を短く取る |
| Lost in the Middle | 中間が読まれにくい | 重要指示を中間に埋めない。長い仕様は分割 |
| Priority Saturation | 同時指示が多いとどれも守られない | 常駐の指示を減らす。条件付き・オンデマンドへ分散 |
| Hallucination | 事実に反する生成をゼロにできない | 検証はモデルの外（ツール、テスト、Hooks） |
| Sycophancy | 正確さより同意を優先しやすい | 合格基準を先に書く。自己レビューしない |
| Knowledge Boundary | 「知らない」と言いにくい | カットオフ後・社内固有は外部参照。答えられない経路を用意 |
| Prompt Sensitivity | 表現で結果が変わる | 曖昧語を避ける。変動させたくない軸は明示 |
| Instruction Decay | 長い会話で初期ルールが薄れる | セッション分割、再注入、機械的強制 |

連鎖の見方:

1. 空間: 長くなる → 中間が死ぬ → 指示が飽和する
2. 信頼性: 知らない → 幻覚 ↔ 追従
3. 時間: 上の問題が長い会話に合流して Decay になる

横断原則（製品非依存）: **入力を短く保つ。重要な指示を埋もれさせない。検証をモデルの外に置く。**

## よくある失敗

- 窓サイズ（200K / 1M）を実効品質と同一視する
- 長い仕様・履歴・ツール定義を常時全部載せる
- 「モデルが覚えておく」を Memory 代わりにする

## 代替・例外

- 個別の低下率（50K で劣化、中間 30%、遵守率 15% 等）は研究・評価設定依存。閾値の公式ではない。方向だけ採る。
- 幻覚を「ゼロにする手法」は採用しない。被害半径を小さくする。
