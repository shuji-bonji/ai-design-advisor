# モデルクラスの選定（SLM / LLM / Reasoning / Multimodal）

- status: canonical
- dimensions: D1, X
- sources:
  - knowledge/primary-sources/slm-vs-llm.md
  - D2 reasoning-effort（思考量はサイズと別軸）
  - 実務インタビュー系（量子化・オンデバイスはサイズ選定と同時に出る）

## 判断の問い

- タスクは狙い定型か、開いた多段推論か
- レイテンシ（体感・QPS）とコストのどちらが先に壊れるか
- データを外に出せるか。オンデバイス必須か
- 知識の広さ・鮮度はモデル内で足りるか、RAG/ツールで足すか
- 「考える量」が要るか（Reasoning はサイズと別軸）

## 推奨パターン

| 寄り | 向く仕事 |
| --- | --- |
| SLM | 分類、抽出、ルーティング、定型要約、固定ツールの Function Calling、オンデバイス、高QPS |
| LLM | 開いた推論、長文の合成、複雑なコード、創造 |
| Reasoning | 多段計画・難しいコーディング・エージェント。サイズより Effort で深さを制御 |
| Multimodal | 入力に画像・音声が本質。テキスト化で足りるなら無理に載せない |
| ハイブリッド | まず SLM、自信がない・複雑なときだけ LLM へ上げる |

**データを外に出せないなら、クラウド LLM の性能比較より D1（オンプレ / オンデバイス / SLM）が勝つ。** 他次元は「出せる前提」で組まない。

進め方: まず LLM で型を見つけ、固まった部分を SLM / 蒸留へ移してよい。
小さい＝劣る、ではない。狙い仕事では特化 SLM が勝つことがある。

量子化（INT8 / INT4 等）はクラス変更ではなく **同じクラスのデプロイ形態**。判断は「品質の落ち方を評価セットで見てから」。速度・VRAM のために落とす。品質確認なしの一括量子化はしない。

コンシューマ向けチャット: 体感が厳しいなら SLM or 小さい LLM + RAG。深い問い合わせだけ Reasoning / 大きいモデルへ。

## よくある失敗

- 全部を最大モデル + 最大 Effort にする
- プライバシー要件があるのにクラウド LLM 前提で進める
- 量子化してベンチ1本で「実用可」とする

## 代替・例外

- B 数の境界（1–15B が SLM 等）は流動的。軸は規模ラベルより上記の問い
- ローカル運用の tok/s・VRAM はハードウェア依存。数値は現場で測る
