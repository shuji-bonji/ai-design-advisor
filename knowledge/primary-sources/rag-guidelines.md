# RAG 設計指針（一次情報・実務まとめ as of 2026-08）

## RAGが必要になる典型ケース

- 知識カットオフを超えた最新情報・社内固有情報が必要
- 回答に根拠（Grounding）を持たせたい
- ハルシネーションを抑えたい
- ドメイン特化の知識を、Fine-tuningなしで活用したい

## 主要な設計ポイント（制御点）

1. **データ準備・コンテンツ品質**  
   - 見出し構造、リスト化、略語定義、社内用語の説明を文書側で整えると検索・生成の両方が改善する（AWSなどの推奨）

2. **Chunking**  
   - 単純な固定長より、意味的な境界を意識したセマンティックチャンキングが現代のデフォルトになりつつある  
   - オーバーラップやメタデータ付与が精度に大きく影響

3. **Embedding 選定**  
   - 検索品質の上限を決める。ドメインに合ったモデルや、ハイブリッド（キーワード + ベクトル）を検討

4. **Retrieval 戦略**  
   - Naive（ベクトル検索のみ） → Hybrid（BM25 + ベクトル） → Rerank → Adaptive / Agentic と段階がある  
   - 多くの実務では Hybrid + Rerank までで十分な改善が得られる

5. **Query 処理**  
   - クエリの言い換え（rephrasing）、拡張、ルーティングが有効なケースが多い

6. **生成時の Grounding**  
   - 取得したチャンクを明確に参照させるプロンプト設計  
   - 「根拠がない場合は答えない」などの指示

7. **評価の分離**  
   - Retrieval品質（Recall / Precision）と Generation品質を分けて測る  
   - 実ユーザーの質問分布を反映した評価セットが重要

## 成熟度のイメージ（実務的な段階）

| レベル | 内容 | 備考 |
| --- | --- | --- |
| 1 | Naive Retrieval + LLM | 最低限 |
| 2 | Hybrid Retrieval | 比較的低コストでRecall向上 |
| 3 | + Rerank | 精度の大きな改善点 |
| 4 | Adaptive（クエリルーティング・書き換え） | 複雑クエリ向け |
| 5 | Agentic RAG（多段検索・自己反省） | レイテンシ・コスト増。必要な場合のみ |

## よくある失敗

- チャンク設計の甘さ（文脈が切れる・重複過多）
- 検索精度を測らずに生成側だけをチューニングする
- 古い情報や権限のない文書が混ざる
- 「答えられない」ケースの扱いが弱い

## エージェントとの関係

- 単純RAGで足りるケースが多い  
- 多段検索やツール選択が必要な場合に Agentic RAG / Tool Calling エージェントへ進む  
- Anthropicなどの推奨でも「まず単純に始め、必要が証明されたら複雑化する」
