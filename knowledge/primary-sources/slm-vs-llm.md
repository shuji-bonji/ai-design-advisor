# SLM vs LLM 選定指針（一次情報・実務まとめ as of 2026-08）

## 基本的な違い

| 観点 | SLM（Small Language Model） | LLM（Large Language Model） |
| --- | --- | --- |
| 規模感 | おおよそ 1B〜15B 程度（定義は流動的） | 数十B〜数百B以上、または同等の能力 |
| 強み | 低レイテンシ、低コスト、オンデバイス/プライバシー、高頻度処理 | 深い推論、広い知識、長文脈、エージェント的複雑タスク |
| 弱み | 汎用性・深い推論・長文脈で劣ることが多い | コスト・レイテンシ・インフラ要件が大きい |

## 選定の4〜5軸（実務でよく使われる）

1. **タスクの複雑さ・境界の明確さ**  
   - 狭い・定型・測定可能 → SLM寄り  
   - オープンエンド・多段推論・創造的 → LLM寄り

2. **レイテンシ要件**  
   - サブ秒〜200ms級が必要 → SLM強く有利  
   - 数秒許容 → LLMも選択肢

3. **コスト・スループット**  
   - 高QPSでコストが支配的 → SLM  
   - 低頻度・高価値 → LLM

4. **プライバシー / オンデバイス / データ主権**  
   - データを外に出せない・オフライン必須 → SLM

5. **知識の範囲と鮮度**  
   - ドメイン特化で十分（Fine-tuneやRAGで補完可能）→ SLMも有力  
   - 広い世界知識や最新性が必要 → LLM + RAG/ツール

## 実務的な推奨パターン（2026年時点）

- **SLMを優先する場合**  
  分類、抽出、ルーティング、定型要約、固定ツールカタログのFunction Calling、オンデバイスアシスタント、高頻度の内部処理

- **LLMを優先する場合**  
  複雑な推論、長文脈の合成、エージェント的な多段作業、コード生成（大規模コードベース）、創造的生成

- **ハイブリッドがデフォルトになりつつある**  
  ルーターで基本はSLM、信頼度が低い・複雑と判断したケースだけLLMにエスカレーション。  
  コスト削減と品質の両立で最も現実的な構成。

## 注意点

- 「小さい＝劣る」ではない。ドメイン特化や蒸留されたSLMは、特定タスクでLLMを上回ることがある。
- Reasoning Model（深く考えるモデル）は、サイズに関わらず「思考量」を制御できる点が別軸になる。
- まずはLLMでプロトタイプし、パターンが固まった部分をSLMに移す、という進め方も有効。
