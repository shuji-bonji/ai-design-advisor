## 判断の問い

- どの層で止めるか。プロンプト一文だけで止めるつもりになっていないか
- 機械的に検証できることを LLM に任せていないか
- コンシューマ向けか社内かで、層の厚みは足りるか

## 推奨パターン

単一の「ガードレール製品」や system prompt の禁止文では足りない。層を分ける。

| 層 | 止めるもの | 手段の例 |
| --- | --- | --- |
| 入力 | 直接 Injection、過大入力、PII の不用意な投入 | 長さ制限、分類、マスキング |
| 検索・ツール結果 | 間接 Injection、毒された文書・ツール | 出典制限、スキーマ検証、信頼できる MCP のみ |
| モデル | 方針逸脱、秘密の復唱 | system 方針、出力フィルタ（完全ではない） |
| ツール実行 | Excessive agency、コマンドインジェクション | 最小権限、allowlist、サンドボックス、HITL |
| 出力 | 不安全な出力の実行、秘密の漏洩 | 出力はデータとして扱う。リンク・HTML・シェルに生で渡さない |
| 運用 | 検知できない逸脱 | 監査ログ、レート制限、インシデント手順、品質ゲート |

機械で決められること（テスト、スキーマ、権限チェック）は Hooks / CI / ゲートウェイに置く。LLM の「気をつける」に依存しない。

OpenAI が挙げる層の例（製品名ではない）: 関連性分類、安全分類（注入）、PII、モデレーション、ツール危険度、規則ベース、出力検証。**規則ベース（ブロックリスト・長さ上限・正規表現）を LLM 層と並べる。**

コンシューマ向けの最低ライン:

- ツールは読み取り中心。書き込み・決済・外部送信は HITL または持たない
- 個人情報をログ・プロンプト・共有コンテキストに残さない
- 出力をアプリの権限で実行しない
- プロンプト注入を「起きうる」前提で、被害半径を小さくする（権限を狭く）

MCP / ツール導入時:

- 許可リスト（出所不明は禁止）
- 秘密は環境変数 / シークレット管理。ログに出さない
- 入力はスキーマで閉じる
- Shadow MCP を棚卸しする

成熟度の目安: 無管理 → 許可リスト → 監視・監査 → 自動化。多くの現場はまず許可リストまで。

## よくある失敗

- 入力サニタイズだけで Injection 対策完了とする
- ツール説明文に秘密や過剰な権限を書く
- 開発用 MCP を本番に流用する
- 監視がなく、壊れてから初めて権限の広さに気づく

## 代替・例外

- オフライン SLM でも、プロンプト注入と過剩なツール権限は残る。境界がデバイス内に移るだけ。
- 規制業種は層を厚くする前に「データを外に出さない」を先に決める（D1 / X と連携）。
