## 判断の問い

- それはモデルに「読んで守らせる」ことか、機械が「止める／記録する／後処理する」ことか
- 測れる線を、モデルの「できた」に任せていないか

## 推奨パターン

Hooks は五層のどれでもない。**ハーネス（実行境界）の割り込み**である。第六層にしない。

| | 五層 | Hooks |
| --- | --- | --- |
| 何か | 担当の分け方 | 実行の節目への割り込み |
| 守らせ方 | 読ませる | 止める、記録する、後処理する |

使うとき:

- 危険な操作の阻止（確認なしの本番変更を通さない）
- 監査（何をどの引数で呼んだか）
- 合格線の機械測定（スコアが線を下回ったら止める）
- 定型の後処理（format / test / 成果物の置き場）

使わないこと:

- 知識の置き場（→ Skills）
- 外部接続の本体（→ MCP）
- 目的と禁止の全文（→ Doctrine）
- Hooks の中で別モデルに「いい感じに判定」させる（決定論が壊れる）

原則: **判断が要るルールはプロンプト／Doctrine、機械的に検証できるものは Hooks。**

品質ゲート（別コンテキストへの委任）と Hooks（同一実行への割り込み）は止める主体が違う。混ぜると「誰が止めたか」が分からなくなる。

## よくある失敗

- Hooks に長い手順を書いて Skills の複製にする
- 「Hooks に移したから機械的」と思い、中身を LLM 判定にする
- 測れる合格線をモデルの自己申告に任せる

## 代替・例外

- 製品名（Hooks / lifecycle / CI gate）は例。本質は「コンテキスト外で必ず走る強制」
