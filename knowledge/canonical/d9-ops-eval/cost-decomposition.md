## 判断の問い

- 今談の「高い」はどの層か（モデル / 推論形態 / プロンプト / ベクトル / エージェント流れ）
- 最悪ケースのモデルと最長コンテキストで全件を予約していないか
- 走りの上限はループの中ではなく、境界で止めているか

## 推奨パターン

一枚の「推論斜金」で語らない。AWS Lens は層を分けて問う。指標も同じ切り方を採る。

| 層 | Lens の問い | ここで決めること |
| --- | --- | --- |
| 1 モデル | GENCOST01 / AGENTCOST02 | 仕事の複雑さに合わせる。定型は小さいモデル。信頼が落ちたときだけ上げる |
| 2 推論形態 | GENCOST02 | 実時が要るか、バッチでよいか。自前ホストかマネージドか |
| 3 プロンプト | GENCOST03 | 入力長さ、出力長さ、繰り返す接頭辞のキャッシュ、無関連入力の落とし |
| 4 ベクトル | GENCOST04 | 次元と件数を用途に合わせる。検索品質を落とさず縮める |
| 5 エージェント流れ | GENCOST05 | 停止条件・回数上限・並列上限。走りを予算する |

Agentic Lens の原則（製品非依存）:

1. **仕事が要る推論だけ払う** — モデル階級・コンテキスト長さ・Reasoning 深さを仕事に合わせる
2. **消費の上限は層ごとに置く** — トークン予算・反復上限・時間・並列。境界で拒否する
3. **再計算の前に使い回す** — プロンプト・ツール結果・検索結果・中間状態のキャッシュ。推論が一番高い
4. **費やした単位に帰属する** — エージェント / テナント / セッション / ワークフロー
5. **コストの計測を設計に戻す** — 一回のレビューで終わらない

コンシューマ向けチャットボットの既定:

- 定型 FAQ は小さいモデル + キャッシュ（X serving-and-cache）
- 難しい問い合わせだけ上の階
- エージェント化しない（D6 段 0–2）。回数上限なしのループを付けない
- RAG は当たった少数 + rerank。チャンク全量を毎回挿むのが一番高い

## よくある失敗

- 全件を最大モデル + 最大 Effort + 全ツール常時接続
- プロンプトを短くせず、モデル斜金だけ語る
- ベクトル次元を評価せずデフォルトのまま
- エージェントの走りを発見してから第一止める
- インフラ斜金だけ見て、セッション単位の推論費が見えない

## 代替・例外

- Bedrock の intelligent prompt routing 等は **vendor_practice**。指標の本質は「階とルーティングを持つ」
- プリクラシファの閾値数字は転記しない
- 自前ホストの予約・量子化は D1 / X。コストの層とは別軸
- カスタムモデルで長期営業する話（AGENTCOST02-BP04）は D7 の要否を通ってから
