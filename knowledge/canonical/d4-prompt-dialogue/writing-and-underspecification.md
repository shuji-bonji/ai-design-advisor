## 判断の問い

- 変動させたくない軸（役割・形式・合格基準）を指定しているか
- 「ちゃんと」「きれいに」など、検証できない語を使っていないか
- 段階的な推論が要る仕事なのに、結論だけ求めていないか

## 推奨パターン

意味が近くても表現で結果は変わる。ただし感受性の大きさは評価法にも依存する。実務の含意は「曖昧だと不安定」。

指定しない軸は、モデルが事前分布の最頻パターンで埋める。判断しているのではない。だから対策は「うまく判断させる」ことではなく、**固定したい軸を明示すること**。

| 悪い | よい |
| --- | --- |
| テストをちゃんと書いて | public メソッドにテストを付ける。配置と構造を指定する |
| レビューして | 観点（セキュリティ / 契約 / テスト）と合格線を指定する |

技法の使い分け（用語レベル）:

- 出力形式が決まっている → 形式を明示。必要なら例（Few-shot）
- 多段の理由付けが品質に効く → 手順を踏ませる（CoT 相当）。ただし Reasoning モデルでは「考えろ」重複に注意（D2）
- 対話ボット → 履歴方針（何を残すか、いつ要約するか）を先に決める（D3）

常駐テキストは小さく始めて、失敗を見て足す。肥大したら条件付き・オンデマンドへ移す。

検証はプロンプトの外（D9 Hooks / テスト）。書き方だけで品質を保証しない。

## よくある失敗

- 軸を指定せず、セッションごとに形式が変わる
- Few-shot の表層フォーマットだけ変えて「プロンプトが効かない」と結論する
- Reasoning Effort と CoT 指示を二重に積む（D2 と衝突しうる）

## 代替・例外

- 「76 ポイント差」は特定モデル・フォーマット変更の報告。一般閾値にしない
- Temperature を上げるほど指定欠落の埋まり方が揺れる。決定的な業務は低 Temperature（D2）
