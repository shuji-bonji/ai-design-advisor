## 判断の問い

- 最適化したいのは **品質のゆれ** か **トークンの席** か
- 長いのは常駐か、今回の入力か、出力か
- その長さは毎回払っているか、キャッシュで一回で済むか

## 推奨パターン

手法は二列に分ける。混ぜると「短くしたら壊れた」が起きる。

### A. 品質（ゆれを止める）

| 手法 | 使うとき | しないとき |
| --- | --- | --- |
| 軸を書く（役割・形式・合格線） | セッションごとに出力が飛ぶ | 「ちゃんと」で済ませる |
| 常駐 / 条件付き / オンデマンド / 今回 に分ける | 一枚が肥大した | 全部を system に乗せる |
| Zero-shot | 一般知識で足り、例が足しにならない | 書式が固いのに例を貼らない |
| Few-shot（例） | 書式・ラベルが決まっている | 例だけ表層を変えて「効かない」と言う |
| 手順を踏ませる（CoT 相当） | 多段が品質に効く、しかも Reasoning モデルではない | Reasoning + 「考えろ」の重複（D2） |
| 問題を小さく割る | 条件分岐が多い一発 | 単発で足りるのに分割する |
| 構造化出力（JSON / 鍵付き） | 下流が機械読みする | 人が読む文にスキーマを強制する |

評価セットが無い手法追加はしない。変えたら回帰する（C09 / D9）。

### B. トークン（席を止める）

消費は **入力トークン × 回数 + 出力トークン × 回数**。短くする前に、どちらが支配的かを見る。

| 手法 | 何を減らす | 条件 |
| --- | --- | --- |
| 常駐を痩せる | 毎ターンの固定費 | 禁止と合格線だけ残す。手順はオンデマンド |
| 入力を貼らない | RAG / MCP の全文 | 当たった少数 + 要約。D5 |
| 出力上限（max tokens） | decode 費 | ハード上限と「短く」の両方。一方だけだと流れる |
| 短い回答方針 | 出力トークン | 人が読む文では「1文」まで。分類は Yes/No や鍵 |
| 接頭辞キャッシュ | 繰り返す system / ツール定義 / 長文 | 接頭辞が安定なときだけ効く。中身を毎回変えるとミス |
| 関連部分だけモデルに渡す | 信頼する常駐の再処理 | ユーザー発話と非信頼入力だけを検査・処理する |
| 無関連入力を止める | 長い貼り付け・ジャンク | フィルタはプロンプトの外（D8） |

「別 LLM でプロンプトを短くする」は AWS が挙げるが、**短くした文を評価セットで見てから** 使う。短縮自体が軸を落とす。

### 手順（現場）

1. 今の常駐を印刷し、固定費のトークン数を知る
2. 軸が空なら A を先に直す（短くすると壊れる）
3. 軸が指定済みで席が支配的なら B
4. 変更は 1 箇づつ。回帰セットで品質を見る
5. 繰り返す接頭辞が長いならキャッシュを検討する

コンシューマ向けボット: 常駐は短い方針 + 禁止 + 形式。FAQ は例より検索。出力は 2–4 文が既定。長文の説明はオンデマンド。

## よくある失敗

- 軸を書かずに文章を削る
- Few-shot の例を 10 個乗せて固定費が肥大する
- Reasoning モデルに CoT を足す
- キャッシュさせたいのに常駐を毎回微調整する
- キャッシュ TTL や最小トークン数を他社に転記する

## 代替・例外

- Tree-of-Thought / Least-to-Most は手法名としてのみ残す。黙りで乗せない
- プロバイダのキャッシュ単価・TTL・最小長は vendor_practice
- Temperature を下げるのは D2。プロンプト最適化と並列だが別軸
