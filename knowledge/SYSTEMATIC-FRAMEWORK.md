# 設計判断の体系的フレームワーク

本ドキュメントは、ai-design-advisor の知識ベースを**意思決定の次元（Decision Dimensions）**として体系化するための中核です。  
スキル版の評価指標・チェックリスト版の項目・推奨ロジックの共通基盤になります。

> 方針: Zenn『サクッと始める生成AI用語集』の概念マップを土台に、一次情報で裏取りした実務指針を各次元に紐づける。  
> 未充足の次元は明示し、順次埋めていく。

---

## 各次元の詳細と充足状況

### D1. モデルクラス選定
**状態: 一次情報あり**（`primary-sources/slm-vs-llm.md`, `zenn-glossary/model-classes.md`）

判断に使う主な軸:
- タスクの複雑さ・境界の明確さ
- レイテンシ要件
- コスト・スループット
- プライバシー / オンデバイス
- 知識の範囲と鮮度
- ハイブリッド（ルーター + エスカレーション）の可否

未充足: Multimodal の選定基準、Reasoning Model を「いつ必須とするか」のより具体的な閾値

### D2. 生成パラメータ
**状態: 一次情報あり**（`primary-sources/reasoning-effort.md`, `primary-sources/temperature.md`, `zenn-glossary/parameters.md`）

判断に使う主な軸:
- Temperature（決定的 ↔ 創造的）
- Reasoning Effort / thinkingLevel / effort（思考の深さ）
- 両者が別軸であること
- Reasoningモデルでは Temperature が制限される場合があること

未充足: Top-p / Top-k の実務的な使い分け、プロバイダごとの最新デフォルトの定期更新

### D3. コンテキスト・知識の扱い
**状態: 部分的**

含めるべき内容:
- Context Window の上限と実際の有効長
- 知識カットオフの影響
- 会話履歴の管理パターン（要約・スライディング・重要情報の永続化）
- 長文脈が必要なタスク vs 短いコンテキストで足りるタスク

未充足: 一次情報の体系的収集、Zenn「コンテキスト」「知識カットオフ」章の詳細化

### D4. プロンプト・対話設計
**状態: 未充足**

含めるべき内容:
- Zero-shot / Few-shot / CoT の使い分け
- System / User / Assistant の役割設計
- 対話履歴の扱い（どこまで保持するか）
- 構造化出力（JSON mode 等）の要否

未充足: Zenn第3部の詳細化、各社の公式プロンプトガイドの要約

### D5. RAGの要否と設計
**状態: 一次情報あり**（`primary-sources/rag-guidelines.md`）

判断に使う主な軸:
- RAGが必要になる条件（カットオフ・社内知識・Grounding）
- 成熟度（Naive → Hybrid → Rerank → Adaptive → Agentic）
- Chunking / Embedding / Retrieval / Query処理 / Grounding / 評価

未充足: Zenn第4部各章（Chunking, Embedding, VectorDB 等）の詳細、具体的な評価指標の例

### D6. エージェント化の要否と設計
**状態: 未充足**

含めるべき内容:
- Plain Prompt で足りるか、Tool Calling が必要か、Multi-Agent が必要か
- Tool 設計の原則（説明の質、名前空間、返す情報の粒度）
- Human-in-the-Loop の粒度
- MCP / Skills / Connectors の位置づけ
- 「まず単純に始め、必要が証明されたら複雑化」（Anthropic等）

未充足: Zenn第5部の詳細化、Anthropicのエージェント設計原則・Tool設計ガイドの体系的要約

### D7. Fine-tuning / 蒸留の要否
**状態: 未充足**

含めるべき内容:
- プロンプト + RAG で足りるライン
- Fine-tuning が有効な条件（スタイル固定、ドメイン特化、コスト削減など）
- 蒸留（大→小）の使いどころ
- RLHF / 事後学習の位置づけ

未充足: Zenn第6部の詳細化、各社のFine-tuningガイド要約

### D8. セキュリティ・ガードレール
**状態: 未充足**

含めるべき内容:
- Prompt Injection の脅威と対策
- Guardrail の多層設計（入力側・出力側・ツール側）
- データ漏洩・PII の扱い
- コンシューマ向け vs 社内向けでの強さの違い

未充足: Zenn第8部の詳細化、OWASP / 各社の安全ガイド

### D9. 運用・評価・コスト
**状態: 未充足**

含めるべき内容:
- Latency 目標と測定
- 評価方法（人手 / LLM-as-a-Judge / 自動メトリクス）
- ベンチマークの使い方と限界
- LLMOps（デプロイ・監視・回帰・コスト管理）
- 継続的な評価セットの育て方

未充足: Zenn第9部の詳細化、評価のベストプラクティス一次情報

### X. 横断制約
**状態: 部分的**（ユースケースリスト・Managementリポジトリとの接続メモあり）

常に考慮する制約:
- レイテンシ許容
- コスト感度（トークン単価・スループット）
- プライバシー・データ主権・オンデバイス
- 既存システムとの関係（Web/業務系 vs 組み込み、既存API、権限）
- 説明責任・監査・規制の強さ
- HITL の必須度

## スキル活用時の指標としての使い方（案）

スキルにユースケースを投げたとき、出力は概ね次の構造を取る：

1. **要件の要約**（入力から抽出した制約と目標）
2. **各次元ごとの推奨**（D1〜D9 + X）
3. **推奨構成のまとめ**（モデル / パラメータ / アーキテクチャ / 実装上の注意）
4. **不確実な点・追加で確認すべきこと**

各次元について「推奨」「根拠（一次情報 or 用語集）」「代替案」「リスク」を返す形にすると、指標として機能する。
